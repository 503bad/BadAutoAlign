# 01. 現状分析 — 実装構造と音質劣化の根本原因

## 1. 現行アーキテクチャの要約

処理の流れ（`src/vat/pipeline.py`）:

```
フレーズ分割 → フレーズごとに:
  ピッチ検出 (detect.py: pYIN/CREPE/RMVPE)
  → タイミング補正 T2 (timing.py: ワープマップ構築 → engine.time_warp)
  → ピッチ再検出
  → ピッチ補正 P2/P3 (pitch.py: 補正カーブ → engine.pitch_shift)
  → 10ms クロスフェードで書き戻し (_splice)
```

エンジンは2種（`src/vat/engines.py`）:

- **SignalsmithEngine**（既定）: Signalsmith Stretch（周波数領域・位相コヒーレンス方式）の
  ストリーミング API を ctypes ラッパー（`src/vat/native/`）経由で駆動。
  - `pitch_shift`: hop=512 サンプルごとにチャンクを送り、チャンク単位で
    `set_transpose_factor` を更新（時間変化ピッチシフト）。
  - `time_warp`: 区分線形ワープマップの区間ごとに入力/出力サンプル数の比を変えて
    可変レートストレッチ（`engines.py:83-112`）。
- **WorldEngine**: WORLD（harvest / cheaptrick / d4c）による分析再合成。フォールバック用。

タイミング補正のワープマップ（`src/vat/timing.py`）は、
中帯域エネルギー包絡の局所相互相関によるラグカーブ（0.25s グリッド、傾き制限 0.25、
ガウシアン平滑 σ=0.15s）または音節アンカーから構築される。

## 2. 課題1「バリバリ音」の根本原因

タイミング補正箇所で発生する「バリバリ」（buzzy / crackling）は、単一の原因ではなく
以下の複合と分析される。影響が大きい順に記す。

### 原因 A: レート変化点（ワープの折れ点）が知覚的に敏感な位置にある【設計】

区分線形ワープマップの折れ点＝ストレッチレートの不連続点である。現行実装では折れ点が

- 音節の芯（P-center）近傍（`timing.py: build_warp_map`）
- ラグカーブのグリッド点（0.25s 間隔、**母音の持続中を含む任意の位置**）

に置かれる。母音の定常部でレートが急変すると、位相ボコーダのフレーム合成間隔が
その瞬間に変わり、倍音の位相進行が乱れて周期的なざらつき（振幅変調＝バリバリ感）になる。
ラグカーブ自体はガウシアン平滑済みだが、`WarpMap` へ変換した時点で区分線形＝レートは階段状になる。

### 原因 B: トランジェント（子音・アタック）が伸縮対象に含まれる【設計】

位相ボコーダ系 TSM の最大の弱点はトランジェントの滲み（transient smearing）である
（→ `02_理論_タイムストレッチ.md` §3）。現行のワープは「子音は直前アンカーとの間で
連続的に伸縮される」設計（`timing.py` モジュール docstring）であり、
破裂音・摩擦音が伸縮率≠1.0 で処理されると、エネルギーが複数フレームに拡散して
「バリッ」というスペクトルの濁りとして知覚される。

### 原因 C: `time_warp` のチャンク駆動による量子化とレート階段【実装】

`engines.py:95-107` では区間ごとに最大 2048 サンプル（48kHz で ~43ms）単位で
`process(in=m, out=want)` を呼ぶ。Signalsmith Stretch はチャンク内でレートを一定として
扱うため、実効レートは 43ms 幅の階段になる。また `want = round((fed+m)*ld/ls) - emitted` の
整数丸めで ±1 サンプルのジッタが乗る（これ自体は軽微だが、階段状レートを強調する）。

さらに `ls <= 0 or ld <= 0: continue`（`engines.py:98-99`）は、
dst 区間長が丸めで 0 になった場合に **入力サンプルを送らずスキップ**するため、
ストリーム内部状態から見ると入力が瞬間的に不連続になる（発生頻度は低いが波形不連続の温床）。

### 原因 D: 位相ボコーダ固有の phasiness【エンジン特性】

Signalsmith Stretch は水平（時間）＋垂直（周波数）の位相予測で従来型位相ボコーダより
phasiness を大きく低減しているが、大きな伸縮では「juddery smudge」（設計者自身の表現）が
残る。max_shift_ms=120ms の局所補正では伸縮率は最大 4.0/0.25 倍
（`timing.py:_sanitize_anchors`）まで許容されており、短区間に大レートがかかると顕在化する。

### 原因 E: WORLD エンジン利用時の buzzy 感【エンジン特性】

WORLD 再合成は励振が調和成分＋帯域非周期性ノイズのモデルに落ちるため、
歌声のブレシネスや子音でモデル誤差が「ブザー的」な音になる（既知の品質上限。
→ `03_理論_ピッチ補正.md` §4）。C++ コンパイラが無い環境では自動的に WORLD へ
フォールバックする（`engines.py:26-29`）ため、配布環境によってはこちらが主因になる。

## 3. 課題2「ピッチ補正品質」の根本原因

### 原因 F: フォルマント保持が無効【実装・最重要】

ラッパーには `vs_set_formant_factor` がバインド済み（`native/__init__.py:179`）だが、
`SignalsmithEngine.pitch_shift` からは一度も呼ばれていない。つまり現在のピッチシフトは
**スペクトル包絡ごと平行移動**しており、max_correction_cents=300（3半音）までの補正で
声質が変わる（チップマンク/こもり方向）。商用ツールとの品質差の第一要因。

### 原因 G: tonality limit 未設定【実装】

`set_transpose_factor(multiplier, tonality_limit=0.0)` で常に 0（無効）。
高域の非調和成分（子音・息）までピッチスケールされ、シフト時に高域が不自然になる。
Signalsmith 推奨はコーナー周波数（例 8000/√factor Hz）以上を 1:1 に保つ設定。

### 原因 H: 補正カーブがノート内一定オフセットのみ【設計】

`pitch.py: build_correction_curve` はノートごとの中央値オフセット＋ガウシアン平滑＋
アタックランプという構成。ビブラートが保持される点は正しい設計だが、

- ノート内の**ドリフト**（ゆっくりした音程の逸れ）は中央値では補正されない
- ノート間の**遷移（ポルタメント・しゃくり）**は平滑化任せで、遷移形状の制御がない
- スケール外への大きな補正時、ビブラート振幅や逸脱の「揺らぎスケール」が補正されない
  （深いビブラートのまま中心だけ動くと不自然になるケース）

### 原因 I: チャンク粒度のトランスポーズ階段【実装・軽微】

`pitch_shift` は hop=512（48kHz で ~10.7ms）ごとに transpose を更新する。
カーブは σ=40ms で平滑済みなので通常は問題にならないが、急峻なカーブでは
10.7ms 幅の階段状ピッチ変化になる。

### 原因 J: ピッチ検出の分解能と誤り【前段】

pYIN 分解能 10 セント（`config.py: pyin_resolution`）、オクターブ誤検出・
サブハーモニクスへの飛びは中央値である程度吸収されるが、curve モード
（ガイド F0 転写）ではフレーム単位誤差がそのまま補正カーブに乗る。
RMVPE / CREPE の選択肢は既にあるが、既定は auto。

## 4. 原因と対策の対応（サマリ）

| # | 原因 | 種別 | 対策（→ 05_改修方針.md） |
|---|---|---|---|
| A | レート折れ点が母音芯にある | 設計 | 伸縮の再配置（無音・子音境界へ移動） |
| B | トランジェントも伸縮される | 設計 | トランジェント保護（rate=1 区間） |
| C | チャンク駆動のレート階段・入力スキップ | 実装 | time_warp 書き直し（細粒度＋連続レート） |
| D | 位相ボコーダの限界 | エンジン | 伸縮率の抑制＋（将来）WSOLA/PSOLA ハイブリッド |
| E | WORLD の buzzy | エンジン | フォールバック品質改善は低優先 |
| F | フォルマント保持なし | 実装 | `vs_set_formant_factor` 有効化 |
| G | tonality limit なし | 実装 | 設定追加 |
| H | 補正カーブが単純 | 設計 | ドリフト補正・遷移モデル・揺らぎ制御 |
| I | トランスポーズ階段 | 実装 | サンプル単位補間 or チャンク縮小 |
| J | 検出誤り | 前段 | RMVPE 既定化・後処理強化 |
